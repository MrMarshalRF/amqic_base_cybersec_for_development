# Resilience to jailbreaks and prompt injection in LLM agents

## TL;DR

Treat every model-proposed action as an untrusted request. An independent host must enforce who may use each tool, with which arguments, against which target and for how long. Keep model context, credentials, approvals and execution privileges separate. Release an agent only after demonstrating that permitted work still succeeds and that unsafe or uncertain requests cannot acquire additional authority.

## Where it helps

Use this guide for coding agents, support assistants, retrieval workflows, tool-using models and local model deployments. A persona jailbreak attempts to change the model's behavior by claiming a role or special operating context. Prompt injection occurs when untrusted content is interpreted as instructions. It can enter through user messages, retrieved documents, tool results, issue text, screenshots, attachments or saved memory. Even a known user or approved tool can carry untrusted content. Model refusals and response filters can reduce risk. The trusted application and execution environment enforce authorization.

## Set the boundary outside the model

| Decision | What the trusted owner enforces | What to verify |
| --- | --- | --- |
| Identity and role | Derive the actor, tenant, role and run generation from authenticated state. Keep policy, approval and revocation outside the model's writable boundary. | A role claimed in chat, retrieved text or tool output cannot grant a tool, broaden access or establish approval. |
| Tool, arguments and target | Expose a fixed reviewed tool catalog. Validate structured arguments, reject unexpected fields, and authorize the actual resource, destination and operation. Keep target resolution and execution bound to the checked request. Carry the authenticated caller's scope through delegation. | Extra arguments, another tenant's resource, unsupported input and an unapproved destination are denied before dispatch. |
| Approval, duration and replay | Bind independent approvals to the authenticated actor, run, exact operation, validated arguments and target. Apply expiry, generation checks and atomic replay protection. Set host limits on time, parallel calls, repeated steps and spend. Check those bindings and remaining capacity at dispatch. | Changes to scope, arguments, target or generation need a new decision. An expired approval or replayed operation causes no additional dispatch through this gate. |
| Process, network and secrets | Give workers separate execution identities, bounded filesystem access and deny-by-default network access. Put credential use behind an external broker scoped to the approved tool and destination. Apply these controls to local model runtimes and their helpers too. | A model or helper cannot reach other tenants, control-plane services, unapproved destinations, host credentials or unrelated directories. Operators can revoke access without cooperation from the model. |
| Tool results and final output | Treat returned text, images and documents as untrusted data. Validate typed output and restrict tool-result data sent back to the model. Encode content for the actual output destination and disable automatic outbound fetches where they are unnecessary. Apply reviewed redaction and disclosure rules before presenting or sending output. Require separate approval where applicable for consequential changes. | Any data-dependent follow-up must independently pass trusted admission. Restricted data is withheld even when the requested tool call was authorized. |

Use the [agent runtime guide](AI-AGENT-RUNTIME.md) for deployment design and the [reference guard](../enterprise/agent-runtime/README.md) to see which contracts the kit demonstrates. The reference illustrates argument and approval checks and bounded admission. OS isolation, target and credential enforcement, shared state across replicas and independent human authorization depend on the host and deployment. Review installed tools, dependencies and the effective policy with [agent runtime integrity](AGENT-RUNTIME-INTEGRITY.md) and [static configuration review](AGENT-CONFIG-REVIEW.md) before granting access.

Use a structured model API or a reviewed serializer that keeps message roles and tool-result types under application control. Verify the adapter actually used by each deployment, including local inference or fallback providers. Keep untrusted material in data fields when copying, truncating, serializing or restoring it from memory. Delimiters, filters and claimed personas affect interpretation. The host still applies the same admission decision. Low-risk work can run under a standing, narrowly scoped host policy. High-impact effects require the independent current approval or step-up defined for that action. See [untrusted tool output and role boundaries](AI-AGENT-RUNTIME.md#untrusted-tool-output-and-role-boundaries).

## Preserve evidence without collecting conversations by default

Record metadata needed to reconstruct decisions. Prefer a timestamp, opaque run and operation IDs, authenticated policy version, source category, tool and target category, decision stage and reason code. Distinguish model proposals, host denials, independently approved dispatches, confirmed effects and unresolved results. Keep raw prompts, personal data, credentials, full URLs or tool arguments that can carry sensitive values, screenshots and document bodies out of general logs. If case review requires content, use minimum necessary redacted extracts in a restricted evidence store with an owner, access review and retention limit. Keep untrusted text as data throughout collection and triage.

Use indicators such as role or authority claims, unexpected requests to disclose context, and repeated attempts to cross a tool boundary as review leads. A code comment, incident narrative, educational example or quoted dialogue can contain the same language. Correlate model and host records before concluding that an action was dispatched or had an effect. Missing telemetry leaves that question open. Use the kit's existing [SIEM mappings](../enterprise/operations/README.md) and [configuration-review dispositions](AGENT-CONFIG-REVIEW.md#reporting-and-siem-compatibility).

## Review changes with harmless offline fixtures

Use synthetic documents and typed mock proposals with neutral markers. Keep the fixture runtime offline and without real tools, credentials, sensitive data or production integrations. A mock handler can record whether it would have been called. First exercise the host directly with approved and denied mock requests, then exercise the model-facing data path with mocked results. This gives a host enforcement test even when a model never proposes the disallowed action. Optional public incident or jailbreak corpora belong in a separate, privately managed threat-intelligence workflow with provenance and applicable licensing reviewed. Keep raw examples out of production prompts, agent memory, executable instructions and this kit's fixtures. Keep both testing and deception free of instructions aimed at third-party agents. See [reducing exposure to automated external reconnaissance](EXTERNAL-RECON-DEGRADATION.md#use-inert-deception-only-where-you-can-operate-it) for decoy handling.

| Scenario | Expected decision | Near match or unknown |
| --- | --- | --- |
| A synthetic source carries a test-only marker for a changed role | Treat it as source data. A corresponding mock proposal for an expanded capability is denied and reaches no handler. | An authenticated user with a valid scope can use the existing approved capability. A refusal alone leaves host enforcement untested. |
| A mock proposal has an extra field, a different tenant target or changed approved arguments | Deny at admission and record the reason without the raw input. | The exact typed request for its own tenant succeeds once inside the approved window. An unavailable decision service requires protected calls to wait or deny. |
| A duplicate or expired operation reaches the gate | Prevent a second dispatch and preserve the original outcome reference. | A new authorized operation has its own identity. If a prior effect is unknown, reconcile it with the original handler before deciding about retry. |
| A synthetic tool result carries a restricted-data marker and a second unauthorized proposal | Keep the marker out of the outward response and deny the second dispatch. | A normal result can appear in a permitted answer. Missing output-boundary or dispatch records leave containment unverified. |
| A mock stop event revokes the current run while an operation is pending | Reject later dispatches under that generation and reconcile any operation already sent. | Another approved run may continue within its own scope. If an effect is already underway, revocation alone cannot establish cancellation. |
| A mock job reaches its shared operation budget across delegated workers | Deny further work against that budget and record the reason. | Ordinary work within its remaining allowance completes. If shared state is unavailable, check the original reservation before resuming protected work. |
| A code or forensics sample uses language that resembles an authority claim | Permit the authorized read and review. Require independent host authorization for any proposed effect. | Indicators combined with host denials justify investigation. Missing source or identity evidence leaves attribution unresolved. |

For each case, record the fixture revision, model or adapter configuration, expected and observed decisions, whether a mock handler ran, output disposition, evidence reference and coverage gaps. Repeat the relevant positive, negative and unknown cases when the tool catalog, output policy, retrieval source, model, host or approval flow changes. A paper review or offline fixture measures only the boundary it exercises. It supplies no assurance about production integration, all languages and modalities, or resistance to future prompt attacks.

## Roll out and recover

1. Inventory use cases, trust boundaries and the actual enforcement owner for each permission. Start with read-only tasks, minimal outputs and no unneeded tools or destinations. Record the last reviewed compatible configuration, expected task outcomes and an independently accessible stop procedure.
2. Verify the manual cases with bounded offline inputs. Require a permitted path for ordinary work and an independent denial for the disallowed effect. Exercise the approval and emergency-stop channels outside model control before granting consequential capabilities.
3. Introduce one reviewed capability or scope change at a time in a controlled rollout. Track ordinary task success, unsupported input, unexplained denials, missing events, unexpected egress and effects without matching dispatch records. Pause expansion when acceptance or visibility fails. Restore a reviewed configuration with equivalent restrictions or reduce the capability while investigating.
4. In an incident, stop the exact run and revoke its generation through the external control plane. Revoke its credentials at their issuing authority. Preserve restricted evidence. Reconcile in-flight or uncertain effects at the trusted handler before retrying. Resume only from a reviewed baseline that fixes the failure and passes both ordinary and forbidden cases. See [AI runtime operations and emergency stop](AI-AGENT-RUNTIME.md#operations-and-emergency-stop).

## Selected primary sources

- OWASP's 2026 edition covers prompt injection, minimizing model-visible data, mediating actions and validating output at its destination. [OWASP LLM01:2026 Prompt Injection](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md), [OWASP LLM02:2026 Sensitive Information Disclosure](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM02_SensitiveInformationDisclosure.md), [OWASP LLM03:2026 Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md), [OWASP LLM10:2026 Improper Output Handling](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM10_ImproperOutputHandling.md)
- MITRE ATLAS describes prompt injection and jailbreak as distinct techniques. `AML.T0051.000` and `AML.T0051.001` distinguish direct and indirect injection. `AML.T0054` covers jailbreaks. These labels describe behaviors for case review. [MITRE ATLAS 2026.10 technique data](https://github.com/mitre-atlas/atlas-data/blob/main/dist/v6/ATLAS-2026.10.yaml)
- NIST's Generative AI Profile identifies information security and data privacy risks and describes lifecycle risk management and evaluation practices. [NIST AI 600-1, Generative Artificial Intelligence Profile](https://doi.org/10.6028/NIST.AI.600-1)
- MCP security guidance covers concrete authorization hazards such as token passthrough and confused deputies. MCP deployments still need host-specific execution and output controls. [MCP security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
