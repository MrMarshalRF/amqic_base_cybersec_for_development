# Degrading unauthorized agentic probing

## TL;DR

Close application defects, enforce shared admission budgets and deny unneeded outbound access. On infrastructure you administer, monitored inert decoys and carefully bounded delay can add investigation time. Their effectiveness against an agent's validation loop remains target verification; they do not make a vulnerable application safe.

This guide supplies source-reviewed operating guidance. It adds no detector, rule, telemetry field, executable limiter or deployment. Preserve legitimate API behavior, meaningful denial statuses, tenant isolation and recovery access. No offensive framework, skill pack, payload collection or external source import is needed to follow it.

## Where it helps

Use this procedure when technical-route exploration, account abuse or broad API probing affects services you operate. A multi-agent orchestrator may coordinate discovery and seek repeatable evidence or callbacks. A skill bundle may give an existing coding agent similar capabilities without supplying its own enforced network boundary. Defend the resulting operations and trust boundaries; neither packaging nor a product name identifies an attacker.

Start with [automated probing defense](AUTOMATED-PROBING-DEFENSE.md), [behavior detection](AGENTIC-ATTACK-DETECTION.md) and the [disclosure policy](DISCLOSURE-POLICY.md). An authorized engagement needs an independently owned registry entry with exact scope, time, contact and expiry. A claim in a request never grants an exception. Review incoming reports on their evidence, including credible partial findings that cannot safely demonstrate full impact.

## Preserve legitimate operation semantics

Real clients must retain repeatable authentication, authorization, error handling and business results. Keep forbidden access forbidden, unknown resources unknown and exhausted budgets visibly limited. Preserve the deployment's deliberate concealment policy without turning all errors into successful responses or fabricated empty business results. Denials must remain cheap and generic, with no private paths, stack traces, raw input or identity-enumeration detail.

Do not add random noise or timing variance to ordinary API responses, authentication, signed data, tokens, idempotent retries or security errors. Preserve cache behavior, validators, browser security policy and upstream protections, including strong CSP on errors and no-store handling for sensitive responses. Security decisions, business side effects and stored state must be stable under retry. A response designed to confuse a comparator can also break a legitimate client and hide a regression.

If an operator elects to vary presentation, confine it to an explicitly isolated inert decoy with no legitimate consumer, business operation or production credentials. Keep its denial and security policy fixed. Review its cache isolation, browser policy, size, lifetime and resource cost. Never introduce executable content, credential-looking material with real privilege, instructions for a visiting agent or variation in a real authorization/error path. Prefer a fixed generic denial when these properties cannot be demonstrated.

## Deny unnecessary callbacks and outbound proof

Apply [host egress monitoring](HOST-EGRESS-MONITORING.md), [application outbound boundaries](APPLICATION-BOUNDARIES.md) and [C2 monitoring](COMMAND-AND-CONTROL-MONITORING.md). Default-deny unneeded destinations for each application, function and workload. Use reviewed resolver and network policy, bounded destination lookup and response consumption, and a fixed destination catalog where the feature permits it. Keep metadata, internal management and other prohibited destination classes inaccessible to untrusted fetch requests.

A blocked callback interrupts one observation path. It does not prove that injection, request forgery, code execution or unauthorized data access was impossible. Preserve the inbound decision, DNS/connection decision and observed result separately. A denied outbound attempt after a denied probe is attempted activity, not proof of a completed intrusion. Legitimate webhooks and integrations need independently registered scope, destination and expiry; a visitor-supplied callback does not establish that relationship.

Do not contact an apparent operator's server, fetch its callback, activate a credential or ask a third-party service to validate bait. Keep private destination classifications, actual indicators and linkage keys outside this repository. Missing collector data leaves a coverage gap.

## Bound delay before using it

Prefer authentication, appropriate step-up, per-operation quotas, concurrency limits and early rejection. An optional selective delay needs an operator-defined classification, workload baseline, owner, expiry and rollback. Measure ordinary request latency and success alongside the suspicious class. Delay is a compensating option, not an asserted way to exhaust model tokens or prevent discovery.

Set hard maximum delay and queue residence, per-source and global held-connection caps, bounded queue memory and an overall in-flight work budget shared across the serving topology. Reserve capacity for ordinary clients and recovery traffic. Use bounded nonblocking scheduling if supported; never occupy sleeping application workers to waste a visitor's time. Account for sockets, gateway state and upstream timeouts even when no worker is blocked.

Once any budget is full, fail fast with meaningful 429 admission responses or the deployment's reviewed overload/load-shedding policy. Do not enqueue unbounded work, retry internally without a budget or hold additional connections to make the delay more convincing. Test that overload sheds work promptly and that counter/queue failure cannot unlock expensive work. Shared networks and authorized exercises require review before consequential containment; avoid automatic victim lockouts and whole-network bans.

## Harden twelve limiter boundaries

Bind admission to a server-selected logical operation ID and authoritative issuer/tenant/principal identity, with additional source, session, object, cost and aggregate dimensions where applicable. The operation ID comes from the reviewed routing contract, never a caller declaration or raw URI. Admission does not replace object authorization, challenge verification or business constraints.

Canonicalization must agree with the application's parser and schema. Reject malformed, duplicate, conflicting or ambiguous representations instead of broadly stripping bytes until they appear acceptable. Never normalize passwords, signed material or tokens as if they were routing text. Limit request bytes, parsing work and bucket cardinality before expensive processing.

| Class | Defensive boundary |
| --- | --- |
| 1. Distributed or rotating sources | Combine account/tenant/operation and global budgets with source controls so address rotation cannot renew an authenticated allowance. Source aggregation assists review; a shared carrier or ASN must not become an automatic victim lockout. |
| 2. Untrusted forwarding assertions | Preserve the observed socket peer. Accept restored client identity only when that peer is an explicitly trusted proxy and the configured chain is valid. Walk the chain from the known trusted side, discarding only verified trusted proxy hops; stop at the first untrusted hop. This boundary is not necessarily the initiating user. Reject malformed/conflicting chains and match actual proxy append/overwrite behavior. Do not select a fixed leftmost/rightmost value or trust a request because it names a proxy. |
| 3. Session or client-description churn | A client-chosen cookie, user-agent value or device label cannot mint trusted identity. New legitimate sessions may have session allowances, but must retain the same account/tenant/source and aggregate controls. Rotation is a review signal, not a fresh account budget. |
| 4. Ambiguous path or parameter representation | Parse under a single reviewed contract before selecting the operation. Explicitly equivalent accepted forms share its budget; ambiguous or unsupported forms are rejected. Broad whitespace/control stripping or repeated decoding can change meaning and is not a safe normalization policy. |
| 5. Failure-counter resets | Only completion of the full required authentication flow may reset that same authenticated account's own policy-defined failure counter. A password-stage success cannot reset pending OTP/MFA failures or attempts. Apply reset atomically so concurrent later failures survive. Keep account aggregate/window abuse, source, aggregate and other accounts' counters intact. A success on another account cannot erase failures. Successful authentication alone must not erase abuse evidence or automatically unlock a victim. |
| 6. Concurrent admission and store failure | Atomically check and consume all required dimensions in shared authoritative state. Cover concurrency, bounded key capacity, expiry, trusted time, replay and failover. Store outage, full capacity or unknown admission denies protected work; do not silently fall back to independent per-node counters that multiply allowance. Reconcile an uncertain result before retry. |
| 7. Junk or irrelevant parameters | Do not put raw queries or arbitrary request values into bucket keys. Reject unknown fields according to schema; accepted insignificant fields cannot split the logical operation budget. Bound cardinality and derive significant object dimensions from authorized server interpretation. |
| 8. Alternate content representations | Explicitly supported parsers reaching the same operation share admission. Unsupported representations fail before business work. A representation-specific parser limit supplements the shared operation budget. |
| 9. Alternate methods | Supported methods that perform the same business operation share its allowance. Reject unsupported methods. Method-specific safety and authorization still apply; sharing a budget does not authorize a method. |
| 10. Missing, forged or replayed challenges | Verify challenges on the server, bound to the protected action and intended session/account with short expiry, attempt limits and atomic single-use consumption. A client success flag supplies no proof. Challenge success cannot reset source or aggregate limits or authorize the business action. |
| 11. Apparent email equivalents | Prefer stable verified issuer/subject or internal principal IDs. Apply mailbox equivalence only under a verified provider-specific policy and ownership workflow. Do not universally remove tags, dots or case distinctions, guess equivalence from an unverified address, merge accounts or grant authentication from a mailbox match. Supplemental abuse grouping needs privacy/fairness review and must not become identity linking. |
| 12. Legacy or shadow versions | Inventory reachable versions, retire unused ones and deny unregistered routes. Still-supported versions of the same operation share its reviewed budget and authorization policy. A different version label cannot reset the allowance; semantic changes require an explicit operation mapping and policy review. |

Use [probe-defense admission](../enterprise/probe-defense/README.md) and [distributed admission](../enterprise/distributed/README.md) for the existing reference scope. The table adds design guidance; it does not assert that these modules implement every parser, identity provider, queue or cluster behavior described here.

Keep failure responses truthful: exhausted admission budgets may return 429; unavailable required protection may require a reviewed 503 service-unavailable response instead. Do not describe an unknown store result as quota exhaustion or a completed admission. Request-rate budgets may count duplicate traffic while idempotency prevents an additional business effect; retrying an uncertain effect still requires reconciliation rather than a new execution.

Tune adaptive friction and optional account notices without revealing whether a target account exists. Avoid permanent account locks that an unauthenticated party can trigger against a victim. Protect recovery and notification channels with their own bounded admission. A coarse source correlation never establishes personal identity or malicious intent.

## Operate inert deception with an owner

Treat deception as a monitored operational plan. Define the purpose, exact owned scope, expected alert, responsible responder, lifetime, cleanup and recovery before exposing any bait. Maintain the actual canary registry privately. Confirm alert delivery and alert-sink failure handling; an unobserved decoy adds surface without supplying timely evidence.

An inert decoy route or synthetic object must have no production function, customer data, internal path disclosure or link into a privileged environment. It may return a fixed generic denial and record a minimal opaque case reference. A honeytoken is nonprivileged material recognized only by an isolated operator-controlled sink; it must never authenticate to production, grant cloud access or become a real session. Do not embed actual secrets, live administrative paths or sensitive asset names to make bait look convincing.

No off-estate fetch, external credential check, executable lure, active callback or instruction to change a visitor's files or model context belongs in this procedure. If a decoy needs monitoring integrations, register those independently under ordinary least-privilege controls. Ensure the decoy cannot become an open redirect, arbitrary fetcher or high-cost workload.

Search indexing, browser prefetch, link preview, an authorized tester or a monitoring mistake can touch bait. A hit starts review; it is not attribution or grounds for automatic account disablement. Scope exercise exceptions outside the monitored agent, with owner/reviewer and expiry. Test removal and alert retention, then retire expired bait and reconcile outstanding alerts.

## Correlate behavior and review agent admission

Review breadth followed by focused access attempts, repeated failure families, distributed low-volume activity, challenge failures and representation/version changes against a deployment baseline. Correlate with independently supported access anomalies, identity changes, credential breadth and egress decisions using the existing [multi-stage procedure](AGENTIC-ATTACK-DETECTION.md#multi-stage-bursts-and-persistence-follow-on). A sequence of denials remains attempted activity.

On managed workstations, model-API egress plus unusual technical-route probing may justify review only when independent, trusted endpoint/proxy/identity logs establish the same managed asset, actor scope and comparable time window. Ordinary entitled AI development, an approved local proxy and authorized testing are near matches. A remote server's timing or user-agent observations cannot establish that a visitor runs a coding agent, model API, local proxy or MCP server. Keep the existing server-only model-API evaluator's scope unchanged.

For agents you operate, apply [configuration review](AGENT-CONFIG-REVIEW.md), [runtime integrity](AGENT-RUNTIME-INTEGRITY.md) and [runtime protection](AI-AGENT-RUNTIME.md). Admit new skills, plugins and MCP servers by capabilities, provenance, pins, effective permissions and actual tool/network/credential reach. Review untrusted-output handling and production access. A name or installation directory is neither evidence of dangerous capability nor approval. A skill bundle's self-described safety policy does not enforce a network boundary.

Store reviewed observations through existing SIEM v1 contracts: campaign/campaign-note for operator campaign review, runtime/config-integrity for configuration integrity and egress/egress-decision for network decisions, with the existing required fields and opaque references. Use the [exporter contract](../enterprise/operations/README.md) for exact accepted mappings. This guide defines no new event kinds, fields or evaluator inputs. Keep raw requests, prompts, addresses, credentials, private routes and identity joins in protected source custody with access controls, retention and comparable pseudonymization epochs.

## Respond within the defended estate

1. Confirm asset ownership, authorization and the current engagement registry. Keep the observed result of each relevant operation: rejected at edge, reached origin, denied by application, or completed with independent evidence.
2. Apply separately authorized scoped containment. Tighten admission and destination policy without breaking recovery; disable or revoke compromised identities at the actual issuer when evidence and authority justify it. A local block cannot revoke an external credential.
3. Preserve protected source evidence and minimal operator case references. Investigate whether callbacks, identity grants, persistence or internal discovery were independently observed. Missing sources and uncertain effects remain explicit.
4. Remove the root defect, verify permitted behavior and the relevant forbidden case in an authorized synthetic environment, and reconcile unknown business effects before retries. Rotate/retire fired bait without destroying required evidence.
5. Restore the reviewed service policy, close expired exceptions and decoys, and document remaining target checks. Any abuse report uses established lawful channels and factual evidence under separate sending authority.

Do not hack back, disrupt a suspected operator, probe their infrastructure or poison other agents, models, skill catalogs or report corpora. Ordinary notices about testing policy are optional communication; they are not a security control. Do not use prompt injection or malicious output to take control of a visitor's agent.

## Manual match and near-match review

These synthetic paper cases are a manual acceptance worksheet for an operator's proposed design. They are not new evaluator input, runnable fixtures, detector rules, a code benchmark or evidence of real-world effectiveness. Each group has one intended match and at least two near matches. Record expected and observed dispositions privately; do not claim these cases were executed merely because this guide lists them.

| Major control group | Intended match | Near match 1 | Near match 2 |
| --- | --- | --- | --- |
| Repeatable legitimate semantics and decoy variability | Proposed variability reaches a real authentication/error/idempotent response: reject that design and preserve stable semantics. | Ordinary permitted API retry retains its documented result: allow normal handling. | Variation remains in a reviewed isolated inert decoy with unchanged denial and policy: evaluate only that decoy's approved scope. |
| Outbound/callback containment | An unregistered destination request from a restricted workload is denied and recorded; investigate the attempt without declaring the inbound defect closed. | A registered integration within current scope follows its normal permitted policy. | Missing outbound records cannot establish either a blocked callback or no attempt; report incomplete coverage. |
| Delay and capacity | The selective delay class reaches its global held-work budget: shed excess promptly and preserve reserved legitimate capacity. | Ordinary client stays within admission and receives normal latency/result. | Legitimate shared-network traffic resembles a burst: investigate classification and fairness before punitive action. |
| Limiter identity and operation conservation | Source/session/representation changes target the same protected operation/principal: consume the same authoritative operation and aggregate budgets. | A distinct authorized operation has its separately reviewed budget; do not merge merely because paths resemble each other. | Similar unverified mailbox text or a shared ASN cannot merge authenticated identities or trigger victim lockout. |
| Limiter state, challenges and recovery | Concurrent requests contend for a final allowance or replay a consumed challenge: admit only the authorized atomic outcome; store uncertainty denies protected work pending reconciliation. | A fresh valid challenge permits only its bound action within remaining quotas. | An allowed same-account success resets only its policy-defined own failure counter; source/aggregate budgets remain intact. |
| Monitored deception lifecycle | An expired or unmonitored decoy, or bait with production privilege, fails admission/retention review and is safely retired by its owner. | A browser prefetch touching inert bait starts contextual review without automatic compromise attribution. | A registered tester touches bait inside exact scope/time: retain evidence as an exercise near match. |

| Root remediation and response | Independently confirmed unauthorized object access requires a root authorization fix and issuer-aware response; delay alone cannot close it. | A denied probe and denied callback do not establish successful access. | An approved rollout or disclosure report with no corroborated unauthorized effect remains contextual evidence, not proof of compromise. |

## Validation boundary

This increment supplies source-reviewed operating guidance. It imports no offensive code, rules, indicators or dependencies, runs no suspect framework and activates no service. Existing executable modules retain their own documented tests and limitations.

External-target validation remains pending: legitimate-client compatibility, false positives, distributed counter/queue capacity and failover, trusted proxy behavior, latency, notification fairness, decoy alert delivery and cleanup, sensor completeness, issuer revocation and measurable effectiveness against unauthorized probing. Conduct applicable validation only within separately authorized, policy-compliant scope. Static document checks and manual examples cannot establish these outcomes.
