# Reducing exposure to automated external reconnaissance

## TL;DR

Remove unnecessary public services, restrict administrative access, and patch deployed components. Then review what the remaining public interfaces reveal about assets and software. Keep private inventory and independent evidence so that a quieter public fingerprint cannot cause operators to miss a vulnerable service.

## Where it helps

Use this guide if you operate public DNS, certificates, web edges, origins, or internet-facing services. External attack surface management (EASM) combines inventory with observations about which services are reachable. This guide covers operator-owned infrastructure and review of existing records. Use ownership records and an explicit scope for each asset, including managed providers and third-party dependencies. Use paper cases or isolated synthetic fixtures for acceptance. Existing request admission and denial behavior are covered by [Automated probing defense](AUTOMATED-PROBING-DEFENSE.md).

## Identify and close exposures

Start with authoritative DNS and certificate-issuance records, cloud and service inventories, load balancer and firewall configurations, and the deployed package or image inventory. Record an owner, public name or asset reference, intended audience, public entry point, allowed upstream path and software evidence for each service. Reconcile discrepancies across these records. An asset with unresolved ownership or inconsistent records needs review before a production change.

| Exposure | Operator action | Evidence to retain |
| --- | --- | --- |
| Retired names, forgotten addresses, or DNS records that still point to deprovisioned resources | Trace each dependency, including mail, delegated zones and certificate renewal. Remove obsolete records in a coordinated decommission and keep required public records intact. Restrict zone-transfer access to approved secondaries where used. | Resource ownership, authoritative record changes, dependency checks and service retirement evidence. |
| Internal names in public certificates or DNS | Use private naming and an appropriate trust chain for internal services when client requirements permit it. Review certificate names before issuance and monitor logged issuance for owned names. Expiry or revocation affects certificate use. Historical Certificate Transparency entries remain discoverable. A wildcard reveals the wildcard name and broadens where the covered key can be used. DNS and other certificates may disclose individual names. | Approved name set, issuer records, renewal ownership and disposition of unexpected certificates. |
| Direct access to an origin behind an edge service | Require the approved edge-to-origin path with network and origin authentication controls suited to the deployment. Preserve known management paths, health checks and failover. Review IPv4 and IPv6, all listeners and every routing path. Removing a public DNS record leaves the firewall and listener policies to enforce access. | Independent edge and origin evidence, permitted path, authentication mode and fallback recovery path. |
| Public management interfaces, stores, brokers, or remote access | Remove unused listeners. Keep required management and data services on restricted network paths with strong authentication and least privilege. Review public object listing and cloud aliases with the provider's ownership records. | Approved exceptions with owner and expiry, effective access policy and current resource ownership. |
| Public credentials or sensitive build artifacts | Check your published pages, scripts and source maps against the release inventory. Remove unintended disclosure and revoke or rotate exposed credentials with the actual issuer. Keep required notices and approved artifacts available. | Artifact reference, issuer-side revocation or rotation confirmation, and the corrected release inventory. |

## Keep patch decisions independent of public fingerprints

Identify the running build from deployment records and supported host inventories. Match the exact vendor package or image against the applicable advisory, including distribution fixes and backports. A missing public version leaves a version-based match unresolved. A reachable store, a visible administrator screen or other independently observed behavior can still provide exposure evidence. Treat exposure and patch status as separate facts. For a likely or confirmed affected deployment, assign an owner and a due time based on reachability, impact, exploitation evidence and the vendor's guidance. Use the CISA and EU known exploited vulnerability catalogs to inform prioritization. Use EPSS as a probability estimate. Keep local deployment evidence as the basis for deciding which systems need remediation. For an emergency edge mitigation, record the scope, fallback and expiry and verify the underlying fix before retiring it.

After reducing access and addressing patch risk, remove optional implementation details from supported public responses. Review default pages, HTTP headers, anonymous build or debug details, verbose errors and public source maps. Keep authenticated diagnostics and necessary liveness and readiness signals for load balancers, orchestration and operators. Use minimal bodies with their expected status codes, and verify healthy and unhealthy states. Preserve TLS and SSH interoperability, identity verification, supported protocol negotiation and required identification fields. Keep copyright, license and attribution notices wherever the applicable license requires them. Confirm the deployed fix using host or image evidence even if a fingerprint changes or disappears.

## Correlate observations across the edge and origin

Use request IDs or other trusted join keys where available. Retain the observation time, service and route category, boundary disposition, related asset or case reference and which sensors were available. Preserve whether a request was denied at the edge, reached the origin, was denied by the application or completed with independent effect evidence. Keep identifiers that can expose users, sensitive titles, request bodies or credentials out of general telemetry. Use restricted, redacted incident evidence when necessary.

Review repeated activity across related services and time windows, including cases where individual source rates stay low. Establish baseline traffic from health checks, search crawlers, certificate services, provider infrastructure and approved testing. Client traits, timing and network provenance are correlation signals. Shared NAT, an autonomous system or a client fingerprint cannot establish identity or initial access. Investigate coverage gaps before attributing activity and avoid blanket NAT or ASN bans. Apply existing operation-level limits and narrowly scoped, time-bounded enforcement where the evidence supports it. Use existing mappings for operator-authored `campaign-note` records in the [SIEM reference](../enterprise/operations/README.md).

## Govern your own inventory tooling

If you already operate external attack-surface tooling, assign an owner and record the allowed assets, collector identities, source locations, approved observation windows, exclusions, data fields and retention. Resolve inherited domains, shared addresses and managed providers before treating them as in scope. Keep the controller console private with strong authentication. Admit inventory reporters and workers under dedicated identities and deny access outside their approved network and asset scope. Give API or MCP consumers read-only access when it meets their needs, and make inventory changes through a separately authorized role. Reconcile controller enrollment, worker egress and deployment records with the approved inventory. Investigate unexpected internal breadth, enrollment or outbound tunnels in context, including documented maintenance and monitoring activity. Use the existing [agent configuration review](AGENT-CONFIG-REVIEW.md) and [command-and-control monitoring guide](COMMAND-AND-CONTROL-MONITORING.md) for admission and correlation boundaries.

Classify inventory records and captured responses or images before sharing them with any model. A string or screenshot can disclose more than its asset identifier. Minimize and redact inputs, approve destinations and verify the actual egress and retention policy. Local model deployments still need process isolation, restricted logs and explicit egress controls. Keep ambient credentials out of the worker. Require trusted evidence and operator review to confirm or close a finding, and keep model-generated checks out of automatic execution. See [host egress monitoring](HOST-EGRESS-MONITORING.md#model-apis-and-interaction-capture).

## Use inert deception only where you can operate it

If the estate already supports monitored deception, identify an exact isolated decoy, owner, expiry, egress policy, alert recipient and retirement procedure. Any marker must be inert and unusable as a credential. Preserve predictable behavior for production listeners and legitimate consumers. Treat a decoy contact as a lead that may come from a crawler, certificate monitor, browser prefetch, approved scanner or a delivery check. Validate alert delivery and retire the decoy if ownership or monitoring lapses. Keep decoy content inert and free of instructions aimed at other agents. See [Agentic probing degradation](AGENTIC-OFFENSE-DEGRADATION.md#operate-inert-deception-with-an-owner) and [LLM agent resilience](LLM-JAILBREAK-RESILIENCE.md).

## Roll out and verify by service

1. Capture the intended access paths, known legitimate callers, deployment evidence, change owner and protected rollback procedure. Define maximum error and latency changes for those callers from your baseline and agree on a rollback trigger.
2. Remove or restrict confirmed exposures and complete or track urgent patches. Preserve operator recovery access. Validate required boundary policies and access paths against the synthetic expectations below before widening a change.
3. Limit optional public metadata in a small rollout. Check normal, unauthenticated and unhealthy responses, certificate renewal dependencies, monitoring and edge failover. If a legitimate consumer fails or telemetry disappears, stop expansion and restore the last reviewed compatible response or monitoring policy while maintaining the required access restrictions and patches. Escalate where that recovery cannot preserve either requirement.
4. Observe campaign correlation and review false positives before enabling scoped enforcement. When an effect is uncertain, check original edge, origin and provider records before retrying changes. Keep coverage gaps visible until the missing observation is restored or the operator accepts the remaining uncertainty.

### Manual acceptance cases

Use these paper cases or equivalent isolated synthetic records. For each row, record the expected disposition, actual reviewer or fixture result, observed boundary, missing input and follow-up owner.

| Scenario | Expected finding | Near match or unknown |
| --- | --- | --- |
| A retired service retains a public alias to a resource its owner confirms was deprovisioned | Open an exposure item and coordinate record removal and ownership review. | An active alias has documented ownership and renewal dependencies. Stale inventory without provider confirmation needs reconciliation. |
| A synthetic policy record shows an application response from a disallowed origin path | Flag the exposure and record where the path was admitted. | Approved edge or management traffic stays usable. An edge denial with missing origin records leaves origin reachability unverified. |
| Public responses show no build version while trusted inventory identifies an affected release | Keep the patch item open and verify remediation from deployment evidence. | A trusted vendor backport may resolve the advisory despite an upstream-looking version. Missing inventory leaves patch status unknown. |
| Several independent observations converge on the same unexpected service group | Review as a possible campaign and verify boundary outcomes. | One shared network's expected health checks may look similar. Missing sensors lower coverage and leave attribution unknown. |
| An inventory worker shows destinations outside its approved estate and the source records agree | Review the active enrollment and egress policy. Contain the exact worker where evidence and authority support it. | A registered monitoring job inside its approved scope has an expected disposition. A missing controller record leaves enrollment or ownership unresolved. |
| A health check still distinguishes healthy and unhealthy responses after metadata reduction | Accept the response behavior for that consumer. | If the monitor expects removed fields, pause rollout and restore compatible semantics. Without its observation, compatibility remains open. |
| A synthetic event records contact with an isolated decoy outside its registered validation window | Review the event in context and confirm sensor and alert delivery. | A planned delivery check or crawler can produce the same signal. A gap in decoy records leaves contact or delivery unresolved. |

This guide supplies operating guidance and manual expectations. Public fingerprints and historical records can be incomplete. Documentation checks establish the state of the guidance. Reachability, false positives, failover, recovery and the effect on external reconnaissance require separate deployment evidence within the approved estate and applicable testing scope.

## Selected primary sources

- Certificate Transparency publishes auditable certificate records. The protocol describes append-only logs. [RFC 9162, Certificate Transparency Version 2.0](https://www.rfc-editor.org/rfc/rfc9162.html)
- HTTP status semantics and the optional `Server` field distinguish application behavior from discretionary disclosure. TLS and SSH retain their own protocol requirements, including the SSH identification exchange. [RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.4), [RFC 8446, TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html), [RFC 4253, SSH Transport Layer Protocol](https://www.rfc-editor.org/rfc/rfc4253.html#section-4.2)
- CISA and ENISA distinguish validated exploitation evidence from a general vulnerability list. FIRST defines EPSS as a probability of exploitation activity in the next 30 days. [CISA KEV inclusion criteria](https://content.govdelivery.com/accounts/USDHSCISA/bulletins/418405e), [ENISA Vulnerability Services](https://www.enisa.europa.eu/topics/vulnerability-services), [FIRST Exploit Prediction Scoring System](https://www.first.org/epss/)
- OWASP describes unnecessary features and sensitive errors as configuration risks. Its inventory guidance covers older deployments, asset retirement and data flows. [OWASP API8:2023 Security Misconfiguration](https://api-security.owasp.org/editions/2023/en/0xa8-security-misconfiguration/), [OWASP API9:2023 Improper Inventory Management](https://api-security.owasp.org/editions/2023/en/0xa9-improper-inventory-management/)
- MITRE ATT&CK distinguishes searches of certificate records from active scanning. Local logs may omit searches of external records. [MITRE ATT&CK T1596.003 Digital Certificates](https://attack.mitre.org/techniques/T1596/003/), [MITRE ATT&CK T1595 Active Scanning](https://attack.mitre.org/techniques/T1595/)
- MITRE describes deception as a planned activity with defined goals and supporting operations. [MITRE Engage practical guide](https://engage.mitre.org/wp-content/uploads/2022/04/EngageHandbook-v1.0.pdf)
